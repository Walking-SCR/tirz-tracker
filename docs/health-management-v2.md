# 健康管理设计方案 V2

更新日期：2026-10-16。承接V1；本版新增检查报告识别、真实来源核对、指标管理及iPhone日历联动。当前仍是设计阶段，未改动线上网页、生产数据库或手机日历。

本轮三张关键界面为：健康首页、图片识别核对、日历与指标管理。含真实指标数据的设计图仅保存在被Git忽略的私人目录 `data/health/design-v2/`，不放入公开前端或公开文档图片目录。准确数值图位于 `data/health/source-order-preview.png`，数据来源核对见 `data/health/source-review.md`。设计图由内置ImageGen生成，仅表达产品布局；真实图表应由库内数据与真实日期计算，不从生成图中反向提取数值或坐标。

## 1. 页面顺序（确定）

健康页从上到下为：健康管理标题/日历入口 → 今日计划 → 肝功能趋势 → 检查记录。底部固定“体重 / 健康”两个导航，现有体重页不变。

今日计划继续覆盖：每日三次口服药、每晚一次外用药、每三天一次甲油。时间由本人按既有医嘱设置。到时未记录显示“待确认”，不直接认定漏服，不给出补服或加倍建议。

## 2. 今日计划的展示

- 首先突出当前待确认项，支持“已服用/已涂药”“稍后提醒”。下面按时间排序显示其他任务，避免在主卡和列表重复统计当前项。
- 当日计数始终基于任务实例，甲油非计划日不算进当日总数。
- 已完成可收起，仍可撤销或修改实际时间；历史与计划分开，误操作不改变固定周期。
- 日历中的事件是提醒载体，不是完成记录。在日历中打开或删除事件不能自动等同于已用药。

## 3. 肝功能的两项核心指标

已从本次附件识别出两个指标身份：

- ALT：丙氨酸氨基转移酶；兼容谷丙转氨酶、GPT等报告名称。
- AST：天门冬氨酸氨基转移酶；兼容谷草转氨酶、GOT等报告名称。

单位、本次报告参考范围、原始名称均随每条观察值保存；不只保存在指标设置中。同名指标更换医院或检验方法，参考范围可能不同。异常色与文字只表示超过本条报告范围，不等于病情或用药建议。

### 图表

- 两张上下排列的小折线图分别展示ALT、AST；不采用双纵轴，不把不同指标的参考范围合成一个正常区间。
- 默认累计，支持近3个月；实际横轴使用经本人核对的检查日期，缺少时可明确采用报告日期，并标明日期类型。
- 直线连接真实检查点，不用平滑曲线或插值制造未发生的检查。时间间距按实际天数处理。
- 最新值、报告日期、该次报告参考范围、较上次的绝对变化在图外展示；图内少量关键数字，点击/拖动查看完整记录。
- 历史参考范围变化时，图中展示对应日期的参考带/阶梯上限，或仅在选中记录时展示该条范围；不把最新范围倒套到所有旧记录。
- 本次五张附件按用户明确说明作为五个独立检查来源，原始识别结果保存在被Git忽略的本地待核对库。前四张日期尚未确认，因此当前来源顺序预览不能冒充正式时间趋势；确认完整日期后再按时间绘图。来源1/2数值相同也不自动合并。

### 添加检查与图片识别

“添加检查”打开居中弹层，支持相册、拍照、一次选择多张、手动输入。

流程：选择图片 → 隐私提示/识别进度 → 自动提取日期及其类型、ALT/AST数值、单位和各自参考范围 → 本人核对/修正 → 保存后刷新图表。

核对页必须同时展示：报告局部预览、识别字段、需要确认项、重复来源提示。报告中存在多个日期时分别保留采样/检查/报告日期，由本人确认趋势采用哪一个；不使用相册日期、上传当天或文件修改时间自动补齐。缺少的年份必须补填，不擅自套用当前年份。现有五份附件按用户指示作为五次检查分别保留，即使两份数值相同也不自动合并。

“读取最新日期”指读取报告中的日期，并按已确认日期计算最新记录，不是把最新上传的一张设成最新检查。补传旧报告不能覆盖较新的结果。

错误设计：

- 识别超时：保留图片，提供重新识别、手动输入；沿用现有20秒界面上限，不强迫反复拍摄。
- 有一项无法识别：保留另一项，不用0代替缺失；提示补填后保存，或明确允许仅保存有值项。
- 疑似重复：列出匹配记录和证据，允许合并到已有报告/确认为独立检查/取消；数值相同不能自动去重。本次五份附件依用户说明作为独立检查保留。
- 图像不完整：指出“报告日期未出现在图片中”，允许补充第二张图片或手动确认，不把相册日期当报告日期。
- 云端保存失败：保留草稿，显示“尚未同步”，不能显示正式入库成功。

## 4. 指标及检查记录管理

本版同时覆盖用户可能指向的两类删除：删除健康指标，以及删除日历提醒。两者不联动误删。

- 添加指标：名称、缩写/别名、单位、默认参考范围（可选）、首页显示开关；ALT/AST预置映射仍可管理。
- 指标管理支持“从首页隐藏”和“删除指标”分开。隐藏不删除历史；删除先展示受影响的记录数，确认后进入回收站，不清空整份报告或其他指标。
- 一键删除指明确可达的单个入口，不代表省略破坏性操作确认；删除后提供撤销/恢复。完整清空历史数据必须有独立明确的二次确认。
- 检查记录支持逐条查看原图、修改日期/数值/参考范围、删除本次检查。删除一份报告应说明影响其中哪些指标，不改变用药计划或iPhone私人日历。
- 上传的完整报告包含敏感信息，原图与识别结果保持私人存储；设计图不展示报告号、个人诊断、姓名等非必要字段。

## 5. iPhone日历：可实现范围与交互

### 网页首版建议：独立“健康用药”订阅日历

由服务端提供个人私密订阅地址，用户点击“添加到iPhone日历”，在iPhone系统中确认订阅。三类计划映射到专用日历，不混入工作、生日或其他私人日历；不向网页索取整个Apple账号或日历数据库权限。

网页可以修改服务器上的计划与订阅内容，但iPhone需刷新订阅后才体现变更；不能承诺即时同步、即时删除或准点送达。是否收到日历提醒、VALARM是否生效、系统提醒开关和时区必须在本人iPhone上实测。

添加/删除入口：

1. “添加到iPhone日历”：开启系统订阅确认，不静默添加；应用端记录“等待本人确认”，不能凭链接被点击就写“已连接”。
2. “发送测试日程”：添加不含病名和药名的测试事件，明确提醒时间，要求本人核对日历显示和实际通知。
3. “停止后续同步”：停止发布后续提醒，展示受影响的计划；iPhone可能暂存旧事件，提示等待刷新或取消订阅。
4. “移除iPhone健康日历”：显示iPhone“日历 → 日历列表 → 健康用药 → 信息 → 取消订阅”的引导。最终删除需本人在系统中完成，网页不能伪装已替本人删除。

事件使用稳定UID，重复添加不复制多份；一日三次使用三个已确认时间的日循环，甲油使用已确认起始日的每3天循环，晚间外用药独立循环。暂停/改期通过稳定事件更新、例外日期或取消后续实例处理；系统缓存的旧提醒未确认消失前不得声称全部撤销成功。

提醒与记录分开：打卡不能保证已缓存的日历提醒立刻消失；可以显示已记录，但不把它当作同步取消成功。默认只用一个提醒渠道，避免日历和网页推送双重轰炸。

### 若要求网页里真正一键增删手机事件

当前纯网页方案不承诺该能力。需要另行引入经本人授权的iOS原生能力，例如EventKit，并且删除需要相应完整访问权限；仅写入权限不能读取/删除已创建事件。这属于额外客户端范围，不在本轮悄悄增加。

不把反复导入.ics文件当成双向日历同步；导入文件之后，网页无法保证更新或删除手机里已有的副本。

来源：[Apple日历订阅与取消订阅](https://support.apple.com/guide/iphone/use-multiple-calendars-iph3d1110d4/ios)、[Apple EventKit权限说明](https://developer.apple.com/documentation/eventkit/accessing-the-event-store)。

## 6. 数据与后续实施顺序

私有数据建议按来源图片、报告记录、指标观察值、用药计划、任务实例、日历事件映射分开。保留数据来源和更改记录；不要把本地待核对数据库误称为线上正式数据库。

实施前置：本人确认本次前四份日期（包含年份） → 确认日历订阅方式符合预期 → 本人真实iPhone测试添加、通知、改期、取消订阅 → 再验收正式日期趋势与UI。

验收新增：同一图片重复上传去重；同值不同检查不被误合并；缺失日期不默认今天；报告日期与检查日期保留类型；AST等参考范围按原报告变化；新增旧报告不覆盖最新结果；删除单项指标不误删其他值；退出账号或吊销私密日历链接后停止后续获取；页面宣称取消提醒前验证终端缓存行为。

本轮交付为更新后的产品/交互方案、设计图，以及本地私人待核对数据。没有部署健康功能、触发实际日历操作或写入生产患者数据。
